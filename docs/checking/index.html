Trust

How a proof is checked

An environment is only as good as its reward. Here is exactly what counts as proved, and what the checker was tested against.

Why Lean makes a good reward

Lean has a small kernel that checks every proof step by step. If a theorem compiles with no gaps, it is true in the system, whoever or whatever wrote the proof. That gives a reward signal nobody has to judge by hand. What the kernel does not check is whether a statement means what a human intended. That is why each task shows the statement in words, and why statements are generated from fixed templates and not written by the model being trained.

The pipeline

  1. Compile. The submitted Solution.lean must compile against Mathlib. If it does not, the reward is 0.
  2. Re-check. A second program, leanchecker, replays every declaration in the kernel from scratch. This catches proofs added to the environment by tricks that skip the kernel.
  3. Compare to the reference. A small Lean program loads the hidden reference and the submission into two separate environments and compares kernel terms, not text. Nothing the submission defines can change how that comparison is read.
  4. Check axioms. Each proof may rest on exactly three axioms that Mathlib itself uses: propext, Classical.choice and Quot.sound. Anything else, including sorry, fails.
  5. Score. The reward is the weighted share of theorems that pass all of the above.

What the checker compares

  • Every definition the task provides must be unchanged: same kind, type and value.
  • Every target theorem must have exactly the statement of the reference, as a kernel term.
  • For tasks that ask the agent to write a definition, the type must match and the value is the agent's own; it is then tested by running it on hidden inputs.

Cheating attempts the checker was tested against

Each of these was written as a real submission and run through the grader. All were rejected.

AttemptResult
Leave a sorry in a proofRejected: depends on sorryAx
Prove by native_decideRejected: adds a compiler axiom
Change a provided definition and prove the new statementRejected: definition differs from the task's
Prove a weaker statement under the same nameRejected: statement differs from the one asked for
Skip the kernel and add a false theorem straight into the environmentRejected by the second kernel run
Declare a new axiom and use itRejected: depends on an axiom that is not allowed

What this does not do

  • It does not judge whether a statement is interesting, only whether it is proved. Task statements come from reviewed generators, and every generator ships a reference proof that is compiled in its self-test.
  • It does not measure difficulty for a given model. That needs baselines, which are published as they are run. What we have measured is a floor: on a sample of proving tasks, one automation call (grind, aesop, simp and similar) closes 15 of 192, and each environment page shows its own figures.
  • A proof that is correct but very slow can time out. Tasks have a time limit, stated in the task file.
